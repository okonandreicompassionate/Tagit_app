# v3 — the build we show Snap, and what it takes to scale

v2 is the working app. v3 is the one that survives a platform review and a
crowd. Two separate problems, and it's worth not confusing them: review is a
checklist, scale is arithmetic.

---

## Part 1 — What v3 has to contain

### The three things that gate Snap approval

Snap reviews integrations in **5–10 business days**, and you can build and test
Login Kit in Developer mode *without* approval — so this can all be done, and
demoed, before the App Store is involved. No published store listing is
required.

The published rejection reasons are administrative: missing demo video, no
privacy policy, a description that doesn't match the app, Snap trademarks in
your branding. "Tagit" is clean on the last one. Which leaves three real gaps.

**1. Block and report.** The one I'd actually worry about. A social app for
teenagers where strangers scan each other, with no way to make someone go
away, is what a reviewer is looking for. Drafted in
[planned/v3/](planned/v3/) — schema, client and a report screen.

The design decisions worth keeping:

- **Blocking is enforced in the database, not the client.** A trigger rejects a
  link between a blocked pair, so a modified app can't route around it.
- **The blocked person is never told.** Telling them invites the escalation
  blocking exists to prevent.
- **Block is offered on the report screen, ticked by default.** Someone who has
  just been made uncomfortable shouldn't have to find a second screen.
- **The confirmation says what will happen**, not "we'll investigate" —
  promising review you can't guarantee is worse than saying nothing.

**2. A privacy policy.** Hard requirement, must be your own, and it doesn't
exist. Cheapest item on this list. It has to be truthful about what Tagit
actually holds: name, handle, photo, Snap score, every scan with time and
place, check-ins, events, and a phone number or email for sign-in.

**3. Delete your account, from inside the app.** Apple requires it, and it's
the honest counterpart to "your card follows you". The RPC is drafted;
it authorises off `auth.uid()` so it can only ever delete the caller's own.

### The thing Login Kit fixes for free

Two pieces of the app currently touch Snapchat unofficially:

- `Snapcode.tsx` pulls images from an endpoint that isn't a documented API.
- `snapchat.ts` scrapes the public profile page to verify a handle.

Both work. Neither is sanctioned, and submitting an integration while scraping
the reviewer's own site is an avoidable risk. **Login Kit returns the display
name and Bitmoji officially**, so approval doesn't just add a feature — it lets
both of those be deleted.

Order of work: build Login Kit in Developer mode, add block/report and the
policy, delete the scraping, record a demo video of a real scan-to-add, submit.

### Also worth carrying into v3

- **Server-side scoring.** `links.points` is still client-supplied. The ledger
  and the daily cap are enforced in Postgres, so the ceiling is low, but it
  isn't zero — and no leaderboard should carry a prize until pricing moves into
  a Postgres function.
- **Measure the Snap add.** `addedOnSnap` is local to each phone and never
  syncs, so the app's core conversion is invisible. One column.
- **Geofence check-in.** Someone can photograph a door code and share it. A
  coarse location check at check-in closes it, at the cost of a permission.

## Part 2 — How this scales

Everything below is arithmetic on the current design, not speculation. The
numbers are what to watch, and the point at which each breaks.

### What breaks first, in order

**1. Realtime connections — around 200 concurrent.**

Supabase's free tier caps concurrent realtime connections in the low hundreds.
`IncomingLinkWatcher` opens one per running app, so **concurrent users is the
cap, not total users**. Two hundred people at one event with the app open is a
completely normal Friday.

*Fix:* on Pro the ceiling rises by an order of magnitude. Beyond that, drop the
persistent socket and poll on the events screen only, or push through FCM
instead of a held connection. This is the first wall and the cheapest to hit.

**2. The leaderboard view — noticeable around 50k links.**

```sql
count(distinct l.to_card) ... from cards left join links
```

That aggregates the entire links table on every request, with no filter. It's
instant at a thousand rows and it is a full scan at a million.

*Fix:* denormalise. `cards.swag` is already a trigger-maintained counter —
add `cards.tags_count` the same way and the view stops touching `links` at all.
Do this before the first big event, not after.

**3. `event_feed` — same shape, same problem.**

It counts check-ins per event on every call, and the discovery screen calls it
on every filter change. Add `events.attendee_count` as a counter maintained by
the check-in trigger.

**4. The links table itself.**

One row per scan, plus one mirrored row. A thousand people averaging ten scans
at one festival is 20,000 rows from a single night. That's nothing for
Postgres, but it grows monotonically and every aggregate above walks it.

*Fix:* the counters above make row count irrelevant to read performance.
Partition by month only if it ever exceeds tens of millions.

**5. Storage bandwidth — the free tier's 2GB/month.**

Event posters are full-screen images served to a feed people scroll. Fifty
events at 800KB each, viewed by a thousand people, is 40GB.

*Fix:* this one needs doing before the feed is promoted at all. Resize on
upload (`expo-image-manipulator` is already installed and unused), cap the
long edge at ~1400px, and put a CDN in front. Supabase Storage supports image
transformations on Pro — use them rather than serving originals.

### The cost curve

| Stage | What you're on | Roughly |
|---|---|---|
| Now — demo, tens of users | Supabase free, EAS free | £0 |
| First real event, hundreds | Supabase Pro (realtime, storage, backups) | ~$25/mo |
| iOS launch | Apple Developer Program | $99/yr |
| Builds without the queue | EAS priority | ~$19/mo |
| Play Store | one-off | $25 |

The realistic first bill is **Supabase Pro plus the Apple account**. Nothing
else is urgent, and EAS priority only buys back the queue time you've already
been losing.

### What isn't built and will be needed

- **Nothing is monitored.** No error reporting, no analytics, no alerting. The
  first time the app breaks for users, you'll learn about it from a person.
  Sentry's free tier covers this.
- **No rate limiting.** `POST /links` and `POST /reports` are open to anyone
  with the publishable key. The daily unique index caps scoring abuse, but
  nothing caps volume.
- **Backups are the free tier's.** Pro gets point-in-time recovery. Worth
  having before real people have real histories they'd be upset to lose.
- **The admin dashboard reads only public data.** Fine for now; the moment you
  need to see scans, check-ins or payments, it needs a server holding the
  service key. See [ADMIN.md](ADMIN.md).

### The one architectural decision to revisit

The app talks to PostgREST directly, which is why it was quick to build and why
the API is portable enough to sell. The cost is that **every rule has to live
in the database** — and this project has already been bitten twice by that:
column grants that silently did nothing, and an index expression Postgres
refused.

That trade is right for now. It stops being right when scoring moves
server-side, because at that point there's a server anyway, and hot paths
(scan, check-in, feed) are better off behind Edge Functions where they can be
cached, rate-limited and instrumented.

Don't pre-build it. Do expect it around the point where you're paying for Pro.

## Suggested order

1. Privacy policy — an afternoon, blocks nothing else.
2. Block and report — drafted, needs wiring and a screen.
3. Account deletion — RPC drafted.
4. Login Kit in Developer mode; delete the scraping it replaces.
5. Demo video, then **submit to Snap** — it waits on their queue, so file it
   before you need it.
6. Denormalised counters, image resizing — before the first real event.
7. Server-side scoring, then Sentry.
